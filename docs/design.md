# 設計

2026-09-30 時点。実装より先にここを書き、実装で分かったことを追記形式で残す（上書きしない）。

## 問題

入力は 1 件の Issue（本文・再現手順・スタックトレース・ラベル）と、1 つのリポジトリの 1 コミット。
出力は、報告された挙動に関係するコードの位置の**集合**と、各位置の確率、および位置どうしの関係（直接 / 呼び出し元 / 同じ設定キーを読む、など）。

1 ファイルを当てる問題にしないのは、原因の箇所と、直すと壊れる箇所が別だからである。

## 先行研究と、残っているもの

この分野は混んでいる。Agentless（階層的に問い合わせる）、LocAgent（ヘテロググラフの多ホップ探索）、CoSIL（呼び出しグラフで探索空間を絞る）、OrcaLoca（優先度つき探索と文脈の枝刈り）、KGCompass（知識グラフ）、RepoGraph（他のエージェントへグラフを供給）、そして SweRank（Issue → コード位置に特化した検索器と再順位器、SWE-bench-Lite 88.69 %）。古典側には BugLocator 以来の IR 手法が 20 年分ある。

したがって「Issue からコードを探す」こと自体は新規ではない。残っているのは 2 点である。

1. **依存グラフ上の集合選択として定式化すること。** 既存はどれも順位つきリストを返す。1 位を当てる問題と、読む側が実際に必要とする「原因とその影響範囲の最小の集合」は別物で、後者は重複の割引を含む被覆の問題になる。劣モジュラなら貪欲に 1 − 1/e の保証が付く。
2. **判定の層を較正つきで差し替え可能にすること。** 既存はエージェントの中のプロンプトとして判定を埋め込んでいる。切り出して、較正を自前で持ち、モデルを設定 1 行で替えられるようにすると、判定器の進歩がそのまま性能になり、1 つの API への依存も消える。

この 2 点で数字が出なければ、clew は既存手法の再実装にすぎない。評価はそこを分けて測る。

## 5 つの段

### 1. 索引

tree-sitter でシンボル（関数・型・定数・設定キー）と位置を取り、辺を 3 種類作る。

| 辺 | 取り方 | 使いどころ |
|---|---|---|
| 呼び出し | 呼び出し式の解決（同一パッケージ内は静的、跨ぐ場合は import の解決まで） | 原因の上流・下流 |
| import | ファイル先頭の宣言 | 影響範囲の境界 |
| 同じ識別子への参照 | 設定キー・環境変数名・エラーメッセージの文字列 | 設定由来の不具合で効く |

索引はコミット SHA ごとに作り、`.clew/index/<sha>.db`（SQLite）に置く。再索引は差分のみ。

**未決**: LSP（gopls / rust-analyzer）に寄せると精度は上がるが、言語ごとに常駐プロセスが要る。最初は tree-sitter だけで作り、精度が足りなければ言語ごとに足す。

### 2. 検索

Issue から問合せを 3 本作る。(a) 本文の内容語、(b) スタックトレースの関数名・ファイル名、(c) エラーメッセージの文字列。
それぞれで BM25 と埋め込みの両方を引き、和集合の上位 50〜100 件を候補にする。

スタックトレースがある Issue では (b) がほぼ正解を含むので、ここで当たった候補には検索段で高い事前確率を与える。無い Issue が難しい場合で、その差は評価で分けて報告する。

### 3. 再順位（コード特化の cross-encoder）

候補を Issue との関連で並べ直す。既定は **Qwen3-Reranker**（Apache-2.0、ローカル実行、MTEB(Code) で評価あり）。

**SweRank**（SweRankEmbed 137M + SweRankLLM）はこの用途そのもので訓練されており最も強いが、cc-by-nc-4.0 なので同梱できない。利用者が自分で入れる任意のバックエンドとして受け口だけ用意する。

### 4. 判定（System One）

上位の候補について、型付き確率で 3 つ問う。

```
state    = Issue の本文（要約せず、長ければ先頭と再現手順を残して切る）
         + 候補のコード片（関数単位、前後 10 行）
質問 1   choice「この箇所は報告された挙動の原因に関係するか」
         supports / partial / opposes / unjudgeable
質問 2   choice「この箇所を変更すると、報告された挙動は変わるか」
質問 3   noul 「この箇所は、報告された環境・設定の条件に当てはまるか」
```

1 つの state に 3 問を同梱する。判定器は `POST /v1/systemone` を話すものなら何でもよい。

| 実装 | ライセンス | 大きさ | 置き場所 |
|---|---|---|---|
| Laya | Apache-2.0 | 421M | ローカル（1 GB 未満、T4 で 33 ms） |
| Kev | Apache-2.0 | 0.8B / 4B / 9B | ローカル or OpenRouter |
| Jev（TypeSafe） | 商用 API | — | 入力 $0.042/Mtok、出力無料 |

**Jev を既定にしない。** 2026-09 の査読前論文が「導出を要する判断（数学・コード・論理）では遅れを取る」「自然な短文を足すと正答の 61 % が反転する」「選択肢のラベル語に引きずられ、紐づけた定義文を見ていない」と揃って指摘しており、そのうち 1 点目は clew の用途に直撃する。較正の数値保証も SLA も公式には無い。

**較正は自前で持つ。** 保留集合に対して isotonic 回帰で較正し直し、較正後の確率だけを出力に出す。第三者の実測では生の期待較正誤差が 0.105、再較正後 0.017。判定器を替えたら較正もやり直す。

### 5. 拡張と集合の選択

上位の候補から依存グラフを 1〜2 段たどり、到達した箇所を候補に足して同じ質問で測る（追加の要求はたどった分だけ）。

最後に、重複を割り引いて最小の集合を選ぶ。同じ関数の呼び出し元を 5 件並べても読む側の情報は増えないので、クラスタ（同一ファイル・同一呼び出し木）ごとに割り引く。形は劣モジュラ被覆の貪欲と同じで、1 − 1/e の保証が付く。

出力は位置ごとに 1 行、`https://github.com/<owner>/<repo>/blob/<sha>/<path>#L<a>-L<b>`、較正後の確率、関係の種別。

## 評価

SWE-bench（および SWE-bench Verified）の Issue と正解パッチの対を使う。

| 指標 | 定義 |
|---|---|
| ファイル再現率 @k | 上位 k 件に正解パッチの変更ファイルが含まれる割合 |
| 行再現率 @k | 上位 k 件の行範囲が正解の変更行と重なる割合 |
| 集合の適合率 | 返した集合のうち正解に触れた割合（余計な箇所を返していないか） |
| 較正誤差 | 出した確率と実際の的中率のずれ（ECE） |
| 応答時間 | 索引済みリポジトリに対する問合せ 1 件の総実行時間 |
| 費用 | 問合せ 1 件あたりの入力トークンと USD |

比較の相手は、(a) BM25 単独、(b) 埋め込み単独、(c) 同じ候補を生成モデルに順位づけさせたもの、(d) 公開されている位置特定段の数字（Agentless、LocAgent、SweRank）。

(a) と (b) を欠いた比較は意味がない。検索だけで解ける Issue がどれだけあるかを先に出す。

上の「残っているもの」2 点は、次の 2 つの差分で測る。

- 集合選択の寄与: 段 5 を切って順位つきリストを返した場合との、集合の適合率と行再現率の差
- 判定層の寄与: 段 4 を切って段 3 の順位をそのまま使った場合との差、および判定器を替えたときの差
